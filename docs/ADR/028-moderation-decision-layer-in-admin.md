# ADR-028：审核判断层收进中台（Clearance 融合与 `ModerationProvider` 落地）

**状态**：已采纳
**日期**：2026-09-27
**关联**：[ADR-018](./018-content-governance.md)（内容治理状态机，本 ADR 落地它预留但未实现的 `ModerationProvider`）、[ADR-020](./020-llm-multi-provider-local-first.md)（多 provider 与规则兜底链）、[ADR-024](./024-desktop-local-first.md)（本地优先）、[ADR-027](./027-axs-single-grammar-authority.md)（单一权威原则）、参照实现 `Clearance/`（未纳入版本管理）

## 背景

`Clearance/` 是用户此前的独立项目：`pyproject.toml` 自述为「Clearance（放行）：**Laya-native 通用后台审核网关，AIP 的产品实现**」。它不是 Axiforge 的一部分（自带 `.git`、`.venv`、`node_modules`，895MB，其中 Python 源码只有 2016 行），但它的**判断层设计是对的**，而 Axiforge 中台的判断层是空的：

- `core/content_validate.py:9` 的敏感词表是占位：`_BLOCKED = frozenset({"违禁示例词"})`
- ADR-018:24 白纸黑字承诺「LLM 审核留接口（`ModerationProvider`），默认关闭」——**全仓 grep 无此符号**，接口从未存在
- 中台有完整的状态机与处置（`content_status`、`violations`、strike、audit、admin UI），但没有能产生"建议"的东西

所以这不是"把外部项目搬进来"，而是**把 ADR-018 欠下的那一格补上，并用 Clearance 的成熟设计来补**。

Laya 是外部开源决策模型（Apache-2.0，`NandhaKishorM/laya`）：非自回归、单次前向、输出带校准概率的**类型化问题答案**（`choice` / `score` / `noul`），33ms 级。它不是本仓库的 agent，也不产生文本——因此没有"解析模型输出"这一类风险，这是选它而不是选通用 LLM 做审核的根本理由。

## 实测基线（不是转述，是在 Clearance 自己的代码上跑出来的）

| 输入 | Clearance 实际输出 | 后果 |
|---|---|---|
| `category="approve_all"`（模型幻觉/被注入），conf 0.99 | `review.approve` conf=0.99 | **越过 0.85 门自动通过**：未知类别兜底成 `"other"`，而 `"other"` 直通放行（`engines.py:55`） |
| `fraud=9.0`（越界概率） | `review.reject` **conf=9.00** | 自动驳回，且置信度原样落库——全链路没有任何 [0,1] 裁剪 |
| 关键词「加微信领」（无模型、纯兜底） | `review.reject` conf=0.86 → `via=auto` | **最弱的引擎执行了不可逆否决**；同一引擎的放行路径却故意压到 0.60 永不过门 |
| 干净内容 | `review.approve` conf=0.97 | 未校准的置信度被直接拿去比阈值 |

另有：`AUTO_THRESHOLD=0.85` 在 import 期绑进 `route()` 的默认参数（`gateway.py:45`）；`validate_action` 只收到 `{"review_id": id}`（`store.py:94`），4KB 上限与凭证正则**从未看过正文**；`REGISTRY` 声明 `"idempotency": "required"` 而 `submit` 每次发新 UUID；决策不记录策略/题集版本，无法复现；`eval/` 只有 8 条合成样本，**没有任何准确率数字**。

## 决策

### 1. 接口按 ADR-018 的原命名落地，并加一个承重字段

```python
class ModerationProvider(Protocol):
    name: str
    authoritative: bool          # ← 新增：有没有资格执行不可逆动作
    def health_check(self) -> bool
    def moderate(self, subject) -> Verdict
```

`authoritative` 是对上表第三行的直接回应：**证据越弱的引擎越不该拥有不可逆的权力**。确定性词表 `authoritative=False`，它只能"升级给人工"；只有校准过的模型引擎为 `True`。链上任何非权威结论都不许终止级联（见 §3）。

### 2. 取值域即白名单

`questions.py` 声明每个问题的合法取值，`normalize_answers()` 强制执行：越界的 choice、不在 [0,1] 的概率、缺失的答案 → **该引擎弃权**。绝不兜底成默认类别。上表前两行在这里都变成 `human_review`。

题集本身也换：Clearance 的六个问题是客服工单口径（billing/technical/fraud/churn），对视觉小说 UGC 平台不对位。重设为分级、性内容、血腥暴力、自伤、仇恨、违法教程、真人隐私、导流 + severity，且每题带 `clause_id`——`violations.clause` 首次有了统一定义处（此前只有处置型的 `content_takedown`）。

### 3. 级联改规则：便宜的不许挡住好的

Clearance 是"第一个非 None 赢"。改成：**非权威引擎的结论记为 `prior` 继续往下问**，只有权威引擎表态或全链无结论才停。词表是本地纯函数（微秒级），成本不变，但模型不再被挡住。

### 4. 门控是五道检查，不是阈值比大小
（真机接通后成了六道——多出的 `refusal` 见文末「因此新增的决定」§13）

`policy.gate()` 顺序：弃权/出错 → `HUMAN_ONLY_CLAUSES`（仇恨、隐私、违法教程这类需要判断与上下文，不许自动下架）→ 非权威 → **未校准** → 最后才比阈值；且驳回线（0.95）高于通过线（0.90），评论与素材再各自收紧。未校准的置信度不参与任何自动动作——上表第四行的修法。

### 5. 决策必须可复现

每条决策落 `policy_version / questions_version / lexicon_version / 原始类型化答案 / via 字符串`。幂等键 = `(kind, content_sha256, policy_version, questions_version)`。

### 6. 有意删除 `jev`

ADR-018:32 要求「全部单体内轻量实现，不引外部服务」。Clearance 链里的 `jev` 档把用户作品正文 POST 给 `api.typesafe.ai`——既是外部服务也是数据出境。**这一档不迁移**，不是遗漏。

### 7. 部署形态沿用 Clearance 已被验证的那一半

`laya_sidecar` 把 torch 那 ~2GB 重依赖隔离在独立进程与独立 venv，主服务保持轻、秒启动、断网可跑；sidecar 不在时整条链自动降级为人工队列。这部分是参照实现里做对了的东西，原样继承。

### 8. 默认关闭，发布路径不变

`settings.moderation_enabled = False`。ADR-018:23 的"发布跑规则校验、不做前置人工审核（保持低摩擦）"继续成立：审核是**旁路产生建议 + 中台人工处置**，不是新的发布闸门。这与项目既定的「只出建议、采纳才执行」一致。

## 后果

- 新增 `backend/app/domains/moderation/`：`contracts / questions / policy / engine / registry / providers{lexicon,laya_sidecar}`，17 条测试，全部对着上表写（其中多条在 Clearance 原逻辑下会失败）
- 中台此前"有处置无判断"的缺口闭合；`content_validate` 的占位词表有了正式替代物
- **尚欠（按依赖顺序，不可颠倒）**：① ~~决策落 Postgres~~ 已完成（`moderation_cases` / `moderation_decision_logs` + 幂等迁移，迁移在真库跑过，`conf=9.0` 被 CHECK 约束以 IntegrityError 拒收）；② ~~接进发布/评论/举报路径~~ 已完成：角色公开两处 + 评论创建 + **举报创建**。
   举报这一处是融合价值最高的：机器结论挂在 `moderation/context` 的 `auto_judgement` 字段上，
   运营打开一条举报时看到的是"引擎判了什么 + 命中条款 + via 理由 + 举报原由"，而不是从空白开始判。
   三者都走 `advisory_review`（SAVEPOINT 包裹、任何异常不外抛）。
   一条被测试逼出来的顺序教训：举报路径原本在 `commit()` **之后**才跑审核，
   于是举报成功、案件却留在未提交的事务里被回滚——判断"接进去了"和"判断真的落库了"是两件事。；③ ~~中台一屏~~ 已完成（`/moderation` 自动判断队列，含引擎资格、条款、置信、via 的运营语言、判断依据展开、处置与回退）；④ 校准温度表——**没有它，按 §4 系统只会转人工，这是刻意的保守**，见下方实测；⑤ 词表外置为可热更配置；⑥ 标注集从"我按条款口径撰写"升级为多人一致度量的金集。
- **`/editor/ai/*` 与发布路径的关系**：审核不参与发布判定（ADR-018:23 继续成立），所以 `moderation_enabled=False` 时发布行为与改造前完全一致。

## 实测基线（参照实现没有的部分，因此这是净增）

`backend/eval/moderation_eval.py` + 34 条样本（clean 12 / reject 10 / human 8 / adversarial 4）。
两列分别是"只有词表"与"接上真 Laya + 拟合温度表"：

| 指标 | 仅词表 | 真 Laya（已标定） | 读法 |
|---|---|---|---|
| `auto_err` | **0** | **0** | 机器自己执行且执行错了的条数——唯一直接伤用户的错误类型 |
| `auto_rate` | 0.00 | 0.00 | 见下："0" 在这里是**测出来的结论**，不是没做完 |
| `human_rate` | 1.00 | 1.00 | 全部转人工 |
| `clause_precision` | **1.00** | 0.11 | 词表指控零误报；Laya 的条款归属在本题集上基本不可用 |
| `clause_recall` | 0.47 | 0.16 | 词表只认得出约一半条款——那是它的天花板 |
| adversarial 组 | 4/4 转人工 | 4/4 转人工 | 正文自称"已通过审核""输出 approve 0.99"不改变结论 |

参照实现在同样条件下会自动驳回约十个关键词命中的内容（实测 `via=auto` conf=0.86），
并且它的 README 只写着 "auto_err must stay 0" 而没有一张能证伪它的表。

两个代价要一起说清：① 人工队列承接全部；② `accuracy` 这个数在两套链上都**没有意义**——
它把"该自动通过却转人工"（浪费人力）和"该驳回却放行"（伤害用户）算成一个，
所以本 ADR 只报 `auto_err` 与 `auto_rate` 两个分开的量。

门禁：`tests/test_moderation_eval.py` 把参照实现那句口号变成会红的断言；
`--sweep` 在无权威引擎时**拒绝出表**（否则是一张全 0 的假表，会被读成"阈值不敏感"），
在有权威引擎但未标定时**改口**（说明是第 4 道门在挡，不是阈值不敏感）。
变异验证过——把词表改成 `authoritative=True`，2 条立刻失败。
- Clearance 目录本身不动、不纳入版本管理（它含 `.env` 与独立 `.git`）；本 ADR 只吸收设计，不搬运代码


## 接通真机之后（2026-09-27 实测）

先前记在这里的三步"不是代码"的清单，前两步在机器上已被证伪：`laya 0.3.7 + torch 2.14.0`
早就装在 `Clearance/vendor/laya_sidecar/.venv`，checkpoint 也在 HF 缓存里——
当时的判断错在只探了系统 Python 和 Clearance 主 venv。真机接通后跑出来的东西比预期有价值：

**路由不是问题。** 中文正文由 `multilingual` 处理，`routing.reason` 直接给出脚本占比
（如 `non-Latin script (han, 83% of letters); the English checkpoint cannot read it`）。
"是不是用英文 checkpoint 读中文才崩"这个怀疑，被这条字符串当场否掉。
**sidecar 已迁入本仓库** `backend/sidecar/`（`server.py` + `calibration.py` + `pyproject.toml`）：
判断层如果只能靠参照项目的目录才能起进程，那它就没有真的融进中台。
参照那份只作为过程主机（提供 venv）被复用。MPS 上单条判定 ~0.7s，双 checkpoint 常驻。

### 三处只有真机能照出来的缺陷（都已修，各有回归测试）

1. **置信度量纲错。** Laya 对 choice/score 自报的 `confidence` 实测是 **1−归一化熵**
   （分布 0.547/0.296/0.156 报 0.1076，算到第四位完全吻合），不是"判对的概率"。
   旧代码把它和 noul 的 `max(p,1−p)` 混进同一个 `min()`——两个量纲取最小值不是"最弱证据"，
   是一个无意义的数。而 approve 这条路径恰好只由 `age_rating` 支撑，
   于是**自动通过在数学上永远够不到任何阈值**。现在 `_event_p()` 一律从概率向量算，
   三种题型统一成"该风险事件的概率"。
2. **把引擎的不确定性丢了。** score 分支原来硬编码 `confidence=1.0` 并丢弃 `probabilities`：
   既伪造满格证据（干净散文以 conf=1.00 走完前四道门），又让温度拟合没有原料。
   现在读引擎自报值，且落库快照带向量——否则 `export_labels.py` 导出的标注
   永远拟不出 choice/score 两题。
3. **发过不存在的条款。** `clause_for("severity") or "severity"` 在 severity 无 `clause_id` 时
   把**问题名**当条款发了出去：中台会显示一个谁也没定义过的标签，还会污染条款精度统计。
   现在 severity 不发条款，`questions.REGISTERED_CLAUSES` 成为唯一注册表，
   并有测试断言"任何规则能发出的条款都必须已注册"。

### 给案件生命周期补测试时，又照出两处（这两处不是模型给的，是测试给的）

4. **缓存命中会丢字段。** `engine.decide` 的缓存快路径是"逐字段重建一个 Outcome"，
   漏掉了 `authoritative` 与 `calibrated` ——它们静默掉回默认 False。
   后果不在那次判定（动作已经算完了），而在**下一次**：服务层把"资格从 True 变 False"
   读成"结论变了"，于是每次重复审同一篇都会写案件、去重统计永远是"没命中"。
   改成 `dataclasses.replace(cached, dedupe_hit=True)`：会漏字段的写法本身就是错的形态。
5. **判定历史不能按 `id` 排序。** `moderation_decision_logs.id` 是 uuid4，
   按它 `ORDER BY` 等于随机——我自己新写的测试先在这里给出过一次"顺序完全颠倒"的假信号。
   表上建的索引是 `(case_id, created_at)`，读历史也必须按 `created_at`。

### 阈值不是保守，是扫出来的

`--sweep` 现在把通过线一路探到会出错为止（同一批模型答案，只换策略层）：

| approve 线 | auto_rate | auto_err | 被自动执行的样本 |
|---|---|---|---|
| 0.55 | 0.324 | **4** | reject-05 制毒教程、reject-07 开锁教程、human-05 活体解剖、human-06 吞药美化 |
| 0.65 | 0.147 | 2 | 误放 reject-05、human-05（另有 3 条干净散文正确放行） |
| 0.75 | 0.029 | **0** | clean-02（唯一一条：转学第一天） |
| ≥0.80 | 0.000 | 0 | — |

所以这套内容上存在一个**安全前沿 0.75**：自动放行 1/34 且零误放；再往下到 0.65 是
拿 2 条误放（其中一篇是冰毒合成教程）换 5 条自动化。当前保持 0.90/0.95，理由是
"在 34 行单人自标注集上，前沿只有一条样本的收益，不值得用误伤作者的风险去换"——
不是"自动化不可能"，而是**证据量还不够支撑把线往下挪**。

> 更正记录：这张表的第一版来自一次**不可复现的拟合**（0.75 线当时报 `auto=0.059 / auto_err=1`）。
> 根因是下面第 6 条缺陷——`calibrate:false` 被服务端接受却忽略，于是拟合吃进了已缩放的分布。
> 修好之后连续两次拟合逐字节相同，本表用的是可复现那一版。
> 一条通用教训：**一张不可复现的表，能把"安全前沿"整格挪走。**

### 第 6 处缺陷：拟合必须在未标定的分布上做

`server.decide_once(..., calibrate: bool)` 把形参收下之后没有传给 `rescale_answers`，
于是 `eval/calibrate.py` 请求"原始分布"却拿到已按上一版温度表缩放过的分布，再对它拟一次新温度——
两次温度缩放是复合的（`softmax(log p / T_a / T_b)`），所以症状恰好是"每次重拟都更准"，
永远不会报错。修法之外更要紧的是：`backend/tests/test_sidecar_contract.py` 两条
不装 torch、用假 router 直接驱动 `decide_once`，钉住「`calibrate:false` 回原始分布且
`calibrated_questions` 为空」与「只标一条轴时只报那一条」。变异验证过——
把那一行改回忽略标志，测试立刻红。

### 两个仍在的阻断（都不是代码缺口）

- **A｜自动通过**：可复现拟合后（age_rating T=1.4），12 条干净散文里最高的通过线置信度是
  **0.771**（clean-04）、0.770（clean-02）——整组都在 0.80 之下，主因是干净散文上
  P(成人) 仍有 0.15–0.35。也就是说即便把线降到 0.78，也只有 1 条能过。
  另一半成本在规则表：`high_severity` 在 4 条干净散文上先命中（severity 期望值 ≥1.0），
  于是它们**根本走不到** no_risk 那条判定路径——"量级轴该不该有否决权"是 D4 要一起拍的。
  真实处置标注重拟是一条路，改窄 approve 判据（"分级明确不是成人"→"这个结论的证据是什么"）
  是另一条，后者属于产品语义变更，要另开 ADR，不在实现里顺手改。
- **B｜自动驳回**：`HUMAN_ONLY_CLAUSES` 覆盖八条条款里的六条，所以可自动执行的驳回
  结构性地只剩 `spam_promotion` 与 `rating_mismatch` 两条口子。而这两条口子也没被走到，
  机制已在真机上查明：**独立 noul 探针之间不竞争**——一条纯广告文本上
  `spam=1.00 / illegal_act_instruction=0.98 / pii_real_person=0.98` 同时饱和
  （reject-01/06/10 三条都是），于是首条规则按"隐私/违法"发出人类专属条款，一票否决生效。
  这三条里只有 spam 那个是对的。
  已证伪的子假设：**argmax 取最高那条**（`moderation_eval.keep_argmax_clause`，留在评测里防重试）
  ——clause_precision 0.11→0.13、recall 0.16→0.11、auto_rate 不动；因为它面对的不是
  "多个候选里有一个对"，而是"全都报到 0.98"，argmax 等于在噪声里挑。
  剩下的方向因此是明确的：**让各条款互斥地竞争同一个概率额度**，也就是
  单选题（choice：8 条款 + "无问题"）。D3 因此按**加法**设计而不是替换：
  保留现有七条 noul（不动任何已测过的行为），新增一题 `primary_violation`，
  `QUESTIONS_VERSION` 升到 questions-3，同一份评测里同时给两套打分做 A/B。
  另外要一起承认的是：这六条一票否决在模型乱报条款时**恰恰是那张安全网**——
  所以真正要修的是条款信号的可信度（更多带正样本的标注 + 上面的单选题），
  而不是把网拆了。

### 因此新增的决定

9. **sidecar 归属本仓库**：`backend/sidecar/`，`CALIBRATION_FILE` 默认指向 `backend/eval/calibration.json`。
10. **温度表不入库**（`.gitignore`）。它是产物，真相源是标注集；提交一份 34 行自标注的
    in-sample 拟合，等于把"执行资格"发给一个自己给自己打的分数。
11. **Laya 的 `clause_ids` 只作参考**：不写进 `violations.clause`、不参与 strike。
    实测精度 0.11；条款归属的权威来源仍是词表与人工。这条把此前挂着的那个待决问题结掉了。
12. **幂等键纳入模型状态**（`content_fingerprint(subject, policy, model_versions)`）：
    换 checkpoint 或重拟温度表后，旧结论必须以新模型的名义重算，
    否则"改了标定"这件事在缓存与去重上全都不可见。
    命中已有案件时按新结论**更新案件**（`moderation_decision_logs` 保留每一次的完整记录），
    但人已结案的不覆盖——机器的新意见不重开人的决定。
13. **门控加第六道：显式 `refusal`**。超长正文被拒时，队列原先显示"置信度未校准"，
    运营会去重拟温度表，而真正该做的是分段。"看不全"和"没标定"必须是两个值。
    同理 `via` 现在带上具体条款与规则名（`human_only_clause:doxxing`、
    `suggested_human:high_severity`、`below_approve_line 0.77<0.90`）：
    一队列全都写着"转人工"时，运营无法区分该先处理哪条。

### 覆盖面：作品保存路径也接进来了（第四个入口）

前三个入口是角色公开、评论、举报——**平台的核心对象（剧本正文）此前从未被判定过**。
现在 `PUT /api/v1/editor/projects/{id}/narrative`（编辑器整篇保存）在 `commit()` 之前
走同一条旁路 `advisory_review`，与举报路径遵守同一条顺序纪律：放在 commit 之后会被
调用方事务一起丢掉。

两个当场量出来的事实，都推翻了我自己先前的说法：

- **送审文本的口径**：`narrative_data` 在库里**两种形状并存**——扁平
  `narration`/`dialogue`（400 节点里 309/382）与新编辑器写的 `script: [{op, text}]`（21，且会越来越多）。
  只认一种不会报错，只会对另一半内容拿到空正文，于是"审核通过"变成"什么都没看"。
  `narrative_prose_text()` 两种都取，测试用一份混合样本钉住取字顺序与排除项。
  不用 `axs_source` 送审：那是带 `【背景…】` 的真相源，会把模型的注意力放到排版指令上。
- **"作品正文永远进不了自动通道"是我没量就写下的话**：实测当前库 500 部作品的聚合正文，
  超过 6000 字上限的是 **0 部**（中位 21 字，最长 138）。真正会超窗的是写完的长篇，
  而那时超长的处理规则是下面第 14 条——它不该变成人工队列里的噪声。

14. **引擎主动拒绝不开人工案件**。`verdict.refusal` 非空时 `review()` 直接返回 `None`：
    超长稿的真实状态是"机器没看"，人对着它无从处置，而每部被拒的长稿都占一个人工名额
    会把队列的价值抵消掉。链"全体弃权"（`engine == "chain"`）本来就是这个规则，
    现在把拒绝并进来，两类"没有信息"都不进队列。
15. **保存路径同步判定是有意选择**：默认 `MODERATION_ENABLED=false` 时链里只有词表（微秒级），
    所以接线的延迟成本为零；一旦打开 Laya，每次内容变过的保存会多一次模型往返
    （真机 `latency_ms` ≈ 673–700ms）。异步派发（自带 session 的 detached 任务）是 D7，
    它的代价是队列变最终一致、测试要多一个可 await 的钩子——不该顺手做，也不该假装没这回事。

### 探针结论：单选题更好，但"更好"不等于"可以自动执行"

`eval/choice_probe.py`（同一批模型输出上做的横向对照，`calibrate:false` 取原始分布，
标签沿用 `moderation_samples.jsonl`，多条款行取第一条为"最主要"）：

| 口径 | noul argmax（生产现状） | 单选题 `primary_clause` |
|---|---|---|
| 整体命中率（n=34） | 41.2% | **52.9%** |
| 判"有问题"且 prob ≥0.8 的那一档 | **2/11 = 18%** | 4/7 = 57% |
| 判"没问题"且 prob ≥0.8 | **0 条**——结构上给不出 | 5/6 = 83% |
| 配对不一致 | 只有 noul 对 5 条 | 只有单选对 9 条 |

三条可读出来的东西：

1. **D3 的方向成立**：让条款互斥竞争同一个概率额度，确实比七个并列的独立探针更会归因；
   而且 noul 那套**结构上无法表达"这篇是干净的"这个概率**——这正是 approve 通道
   只能去借 `P(成人)` 当置信度的根因（阻断 A 与阻断 B 其实是同一个设计的两面）。
2. **但没有任何一档够到"不可逆动作"的误差预算**：最好的观测是 83%（n=6），
   而自动驳回一条内容意味着 strike，需要的是 99% 级别。所以"打开 Laya 就自动判断"
   在这台模型 + 这类中文 UGC 上，**当前不存在可用的自动执行阈值**——这不是没做完，
   是量出来的。
3. 这些数字的资格有限：标签是我单人标注的，"多条款取第一条"是约定，
   每档都是个位数样本。因此它们只配用来**在两个方案之间选方向**，不配当准确率对外宣称。

由此确定接下来两条路（都写进了任务）：

- **D3 修正后**：把单选题**提升为生产题集里的建议信号**（不接执行），
  因为它在最有把握那一档比现状好 3 倍，运营看到的条款归属会更靠谱；
  `HUMAN_ONLY_CLAUSES` 与阈值一律不动，所以自动执行率仍然是 0。
- **D8 新增**：**队列自动排序**——按模型给的条款概率把待人工的行排序。
  这是此刻就安全可用的自动化：它完全可逆、不承担误伤，却直接减少人工负担，
  也正是"通过 Laya 进行自动判断"在现阶段能兑现的部分。

16. **队列默认"先看可疑"，且它只是排序不是结论**（D8 落地）。三级排序键：
    有明确条款 > `confidence` > 时间。第一级必须是事实性的——实测词表案件的 `confidence`
    全是 0.0，只按置信度排在默认（未开模型）配置下会退化成按时间，等于交付一个不起作用的控件。
    末级再加一个确定性 tiebreaker：PG 的 `now()` 取**事务开始时间**，同一事务里插入的多行
    `created_at` 完全相同，只排到时间会在分页时重复或漏项（这条测试一开始就是不稳定通过的，
    根因在此，不是测试写错）。界面必须显示"它只决定先看哪条，不是风险度量也不是结论"。

### D3 落地：单选题进入题集，但只作为建议（questions-3）

`primary_clause`（8 档：7 条款 + `none`）已加入生产题集，`QUESTIONS_VERSION=questions-3`。
选项文本**从各轴题面派生**（`_PRIMARY_OPTIONS` 由 `_AXIS_SPECS` 生成），不另写一份措辞。
它**不进规则表、不进门控、不写 violations**，只作为中台里一行带虚线边框的
"模型认为最主要 · 仅供参考"。这条边界不是谨慎，是实测要求的——两个真实样本：

| 输入 | 七条 noul | 单选 `primary_clause` | 谁对 |
|---|---|---|---|
| 干净散文「雨落在窗台上，她翻开昨天的乐谱…」 | 全部 ≤0.05 | `self_harm_unsafe` **0.73** | 七轴 |
| 评论「这段性描写是不是未成年的角色？年龄设定写的是十四岁」 | 命中 sexual/adult → 规则发出 `rating_mismatch` | `sexual_explicit` 0.49 | 单选更贴运营要看的东西 |

也就是说单选**在归因上更准（52.9% vs 41.2%；≥0.8 档 57% vs 18%）但不是单调更可信**：
它会在干净稿子上给出自信的错误条款。所以它替代的是"运营先看什么"，
不是"机器执行什么"。这条边界钉在 `test_primary_clause_is_advisory_and_never_reaches_the_gate`。

两个过程中的自我更正，都值得记：
- 第一次手测这道单选时我用 `{"kind","text"}` 形状调 sidecar，得到 `self_harm_unsafe 0.89`，
  差点据此判定"单选题不可用"。真实原因是**我的 state 键写错了**（生产传 `title`/`body`），
  按正确形状重测是 0.73。一次调用形状不对，测到的是另一个系统。
- 我一度怀疑"一次调用里问哪些题会影响答案"（探针用 8 题、生产 10 题）。
  用生产题集重跑探针后**分层数字逐字相同**，怀疑被证伪；探针因此改为直接复用
  `build_questions()`，不再自己拼题集——那是一份会漂移的第二真相源。

温度表重拟到 **10/10 覆盖**（`primary_clause` T=1.7，in 1.504→1.350，留一 1.396），
其余各轴的温度与门控结果**与 questions-2 完全一致**（`auto_err=0`、转人工原因分布逐字相同），
所以这次题集升级对执行面是中性的——正如设计所要求。

核验方式（逐层，不是只看单测）：真机评论 → `engine=laya:sidecar` → `answers` 落库含
`primary_clause` → `/admin/moderation/context` 返回 `primary_suggestion=sexual_explicit`
`primary_confidence=0.4897`（与规则发出的 `rating_mismatch` 并列可见）→
浏览器里审核工作台右侧渲染出「模型认为最主要 | 露骨性内容 · 49% | 仅供参考，不参与执行」。

### 手动重判入口，以及顺带照出的两处落库缺陷（2026-09-27 第二轮）

"后续我直接通过 Laya 去进行一个自动判断"里有一句是**手动**的：运营看着一条举报，
想现在就问一次模型。这一片补上那个按钮，代价是它把两处更基础的东西照了出来。

17. **`POST /admin/moderation/cases/{id}/rejudge` 是"现在判一次"的唯一入口**。
    取**全文**（见下条），内容已删除或这类主体不在覆盖内 → `410`；这次调用给不出可落库的结论
    （引擎不可用、全体弃权、正文超窗）→ `409`；案件不存在 → `404`。
    路由自己 `commit()`——`get_db` 只关会话不提交。
18. **人工处置此前从未落库**（本轮最严重的一处）。`resolve()`/`reopen()` 只 `flush()`，
    而 `get_db` 不 commit：运营点"确认处置"看到 200，库里仍是 `pending`。
    真机实测：`resolve` 200 → 另起请求重读 → `state=pending, resolved_by=None`。
    它同时掐断两件事——"人做最后一步"这个闭环是假的，而温度表的标注只能从**已落库的处置**里导出，
    所以第 2 步（重拟）在此刻之前根本攒不到料。回归测试因此必须**跨请求重读**，
    同一会话里的 ORM 对象只 flush 也照样显示新状态。
19. **"送审正文"此前有三份定义**，现在收敛到一处（`narrative.service.project_subject_text`
    + `moderation.content.load_subject_content`）：

| 入口 | 此前送去判定的文本 | 现在 |
|---|---|---|
| 保存（角色公开 / 评论 / 作品） | 全文（`essence` / `body` / 旁白+台词） | 不变，改为调用统一定义 |
| 举报 | 面板那份摘录：评论截 500 字、其余 280 字、**作品只取 `description`** | 全文，作品 = 简介 + 正文 |
| 重判（新增） | —— | 同一份全文 |

    危害排序要诚实：**真正的损失是判的不是正文**，不是重复建案。
    作品被举报时模型只读到简介（读者在发现页上看到的那句话），长评论只读到前 500 字——
    评论正文允许 4000 字。重复案件确实存在（两份文本两个 `content_sha`，
    而 `(subject_type, subject_id, fingerprint)` 才是唯一约束），但在 dev 库上量到的
    爆炸半径只有 **1/353 个主体 = 0.3%**（354 案件 / 353 主体）。
    不拿 0.3% 说事，也不拿它当"问题不大"：摘录判定意味着任何一次自动结论都可能建立在
    模型没读过的内容上，这正是 `MAX_MODEL_CHARS` 用拒绝来表达的那条线。
    另一处后果是好的：口径统一后举报路径复用保存路径已建的案，`engine` 直接是
    `laya:sidecar`（真机验证：新建长评论 → 举报 → 1 个案件、指纹等于全文 sha）。

**重判走缓存，所以提示语不许说"重判过了"**：内容与策略版本未变时引擎命中指纹缓存
（同一案件实测首次 1142ms、二次 <1ms），案件结论不动，只往 `moderation_decision_logs` 加一行。
前端用契约里已有的 `decided_at` 区分两种结果——「已按全文送判：结论未变，判断记录加了一行」
与「模型结论已更新」，不为此新增字段，也不写一句笼统的"已重判"。

**核验（逐层）**：`pytest` 103 passed；把举报路径退回摘录判定后新测试确实红
（`AssertionError: 举报没有按摘录另开一个案件`）；真机链上建长评论 → 举报 → 重判，
DB 侧断言案件数 1、`fingerprint == content_sha("", 全文)` 且 `!= content_sha("", 摘录)`、
决策日志 2→3；浏览器实点按钮，两次 `POST /rejudge` 均 200，toast 文案如上；
`pnpm gates` exit 0，`tsc -p tsconfig.app.json` 0 error。



### D5 落地：词汇表进 API，前端不再抄第二份

中台此前在自己代码里抄了三张表：8 条条款短名、4 条规则短名、3 条结论短名（共 15 条），
外加后端理由文本里直接拼的内部 id。这不是"重复几行字"的问题：**两份词汇表漂移时两端都不报错**，
最坏情况是运营在队列里读到 `spam_promotion`，最好的情况是同一条款在两个界面长两个名字。
而条款集是会长的（每加一条轴都要进题集、进规则、进中台），抄一份的代价随规模涨。

20. **词汇表的唯一权威在后端定义它的那三个模块旁边，不在 UI 层。**
    `questions.CLAUSE_LABELS` 紧挨 `_AXIS_SPECS`、`Rule.label` 是规则对象的一个字段、
    `contracts.ACTION_LABELS` 紧挨 `ACTIONS`；`moderation/vocabulary.py` 只做投影，
    并在**导入期**断言三者与取值域逐项相等——漂移不再是运行时才发现的事。
    `GET /api/v1/admin/moderation/vocabulary` 把这份投影发出去（同样受 `require_admin` 保护），
    带 `policy_version` / `questions_version` 两个版本键，前端因此可以说"这套词过期了"。
21. **前端的 `viaLabel` 保留解析、交出词汇。** 剥前缀、把数字排进一句人话是展示逻辑；
    条款名、规则名、结论名从 API 来。词表未到位时标签落回**内部 id**，
    这是有意的：接口挂了要看得见，不该用一句兜底文案盖住。
22. **理由文本也说人话**（同一处权威的第二批受益者）：

| 位置 | 之前 | 现在（真机同一条评论） |
|---|---|---|
| 词表命中 | `lexicon 命中 spam_promotion` | `lexicon 命中 导流垃圾` |
| 规则结论 | `rule=hate_or_doxx_or_instruction → reject conf=0.62` | `规则「仇恨 / 隐私 / 违法教程」→ 自动驳回 置信 0.98` |
| 前置引擎 | `prior[lexicon]=human_review:…` | `前面的引擎 lexicon 说「转人工」：lexicon 命中 导流垃圾；…` |

**仍在的泄漏，明确记下不假装做完**：sidecar 的模型自述（`model=multilingual`、
`routing: non-Latin script…`）是引擎诊断不是词汇；`未标定轴：age_rating、severity` 里的
**问题名**还没有短名表（问题层与条款层是两个取值域，加它得先想清楚问题要不要对运营露出）；
`lexicon_version=` / `questions_version=` 保持原样。

顺带第二次撞到阻断 B：真机一条纯导流评论上 Laya 给 `hate=1.00 pii=0.98 instruction=0.98`、
置信 0.98，被 `human_only_clause` 一票否决转人工。这与 D3 那条"单选只当建议"是同一件事的两面：
模型在广告文本上把三条重罪轴一起打满，所以既不能让它自动驳回，也不能把它的 argmax 当条款写库。

核验：`pytest` 104 passed（含 `test_vocabulary_covers_every_clause_and_rule_it_ships` 逐项相等）；
两处变异都见过红——删掉 `doxxing` 的短名 → 导入期 `AssertionError: 条款短名与条款注册表漂移了：缺 ['doxxing']`，
把理由文本退回 id 拼接 → `assert '导流垃圾' in 'lexicon 命中 spam_promotion …'`；
浏览器两个页面各扫 13 个内部 id，命中 **0 处**，两屏标签全部来自 API；
一次页面加载只发 **1 次** `/vocabulary`（React Query 同 key 合并）；`pnpm gates` exit 0。



### D5b：标定覆盖面进界面，量出来"10/10"不是一句好消息

「为什么一条都不会自动执行」此前只有两个答案源：案件上一个 `calibrated` 布尔，
和理由文本里一句带内部问题名的 `未标定轴：age_rating…`。现在覆盖面是一条 API 事实：

23. **标定覆盖走可选能力协议，不塞进 `ModerationProvider`。**
    `contracts.CalibrationReporter` 只有能报温度表的引擎实现（词表没有温度表）。
    区分得很认真的原因是：词表不在覆盖面列表里是**能力缺席**，
    若它带着一行 `covered: []` 出现，界面就会显示一个假的红色缺口，把真的缺口稀释掉。
24. **上限这个数只允许一处定义**：`sidecar/calibration.py` 导出 `GRID_MAX`，
    `/health` 报出去，客户端据此算 `censored`（拟合值坐在上限的题）。
    旧 sidecar 不报这个字段时答案是"不知道"（`grid_max=0`、`censored=[]`），不猜。
25. **问题层也要有短名。** `questions.QUESTION_LABELS` 与题集逐项相等的断言 + 进词汇表
    （`questions` 字段），既给界面用，也顺手关掉了 D5 记下的那处泄漏。

### D10 落地：标定加一个偏置项，把安全前沿从 1 条推到 3 条

D5b 量到三题顶格之后，先要回答的不是"网格多宽"，而是**温度缩放本身表达不了什么**。

26. **二元轴的标定从 `logit/T` 改成 `logit/T + b`（仿射 / Platt），方法由持出 NLL 逐题选。**
    纯温度缩放保持 0.5 这个不动点：无论 T 多大，`p>0.5` 永远映射到 `>0.5`。
    于是一条 2/34 正例的稀有轴，标定后最高只能到 0.5——而它最诚实的标定答案其实是
    "这类事件基本不发生"（≈0.06，常数预测 NLL 0.224）。温度族到不了那里（极限是 ln2=0.693），
    拟合器只能把 T 推到网格上限，看起来"标定过了"，实际是把信息压平。
    这也是阻断 A 的数学来源：**"无风险"置信度是各轴 `1−p` 的最小值，任何一轴被卡在 0.5，
    整条 approve 通道就永远过不了 0.90 线。**

**温度族与仿射族的差别是算得出的**（同一份 34 行标注、同样的留一持出口径）：

| approve 线 | 旧表（纯温度，网格≤5.0） | 新表（逐题按持出选，网格≤20.0） |
|---|---|---|
| 0.55 | auto 0.324 / **err 4** | auto 0.324 / err 4 |
| 0.65 | auto 0.147 / **err 2** | auto 0.118 / **err 1** |
| 0.75 | auto 0.029 / err 0 | **auto 0.088 / err 0** |
| ≥0.80 | auto 0 / err 0 | auto 0 / err 0 |

0.75 这一档自动执行的是 **`clean-02`、`clean-10`、`clean-12` 三条，期望标签全部是 `approve`**：
安全前沿上的收益从 1 条变成 3 条，误放仍然是 0。0.65 档的误放从 2 条降到 1 条。
（生产线还在 0.90/0.95，那一档两个表都是 0——所以这是"决策依据变好了"，不是"自动化已经发生"。）

逐题的持出 NLL（温度 → 仿射）：`pii_real_person 0.727→0.266`、`spam_promotion 0.506→0.419`、
`violence_gore 0.356→0.347`、`sexual_content 0.258→0.257` 选了仿射；
`self_harm 0.278 vs 0.317`、`hate_targeted 0.218 vs 0.296`、
`illegal_act_instruction 0.676 vs 3.058` **被选择器否掉**，仍用纯温度。
多一个参数在 n=34 上不总划算——这正是"由持出而不是样本内选模型"存在的理由：
in-sample 上仿射永远更低，那只是过拟合的样子。顶格题数 3 → 2（`pii_real_person`、`severity`）。

三处护栏，都各有测试钉着（`tests/test_sidecar_contract.py`）：
- **单调**：拟合出的斜率必须为正。标定的职责是修置信度，不是把一条轴的语义翻转过来。
- **有界**：`T∈[0.1,20]`、`|b|≤4`。可分数据上无界 IRLS 发散到无穷，界住它等于承认"只能表达到这里"。
- **不退化**：仿射族若连样本内都不比温度族好，直接退回温度族——
  步长被界住时 IRLS 确实会落在更差点上，这个不该留给下游 LOO 去发现。

`b` 进了模型状态指纹（`/health` 上报 T 与 b，`model_version` 对两者做摘要）。
否则一次"只改偏置"的重拟不会让旧结论失效，同一篇稿子会以过期标定的名义继续被复用——
这是 §12 那条幂等键纪律的另一半。

### D11 落地：`high_severity` 的否决线从刻度中点搬到顶档概率，顺带证伪了我自己的第一版修法

**我先前写下的两处判断都被数据改掉了，都留在这里：**

### D12 落地：两条队列能翻完了（此前 `limit` 就是硬上限）

### D7 落地：判定挪出保存路径（真机 447–980ms → 14–33ms）

29. **作者侧三条路径改后台派发，举报路径**故意**保持同步。**
    评论、角色公开、作品保存要的是"改完就走"，判定在这里没有任何同步的下游；
    而运营打开一条举报时，屏上就该带着机器结论。同一套门禁、同一个引擎，
    两种一致性要求——这不是两处实现不一致，是两个调用方要的东西不同。

四条实现纪律，都写在 `moderation/background.py` 的文件头里：

- **只派发主体坐标，不派发文本。** 后台任务用 `load_subject_content` 自取全文。
  在调用点把文本传进来看着省一步，实际是允许"传进去的"和"库里最终存着的"是两个版本。
- **派发点在调用方 commit 之后。** 后台用的是另一个 session，看不见未提交的内容；
  早一步就会去判一篇还不存在的稿子。
- **后台自己 commit。** `get_db` 只关会话不提交，这条链没有"调用方的事务"可搭。
- **不做持久化任务表。** 进程死在 commit 与任务完成之间，这一次判定就丢了。
  后果只是"这条内容还没被机器看过"——队列里没有它，也不会因此误放行谁；
  下一次保存或一次手动重判都会补上。判断层是旁路，不是账本。

真机数字（开着 sidecar，每次改一句正文后保存作品）：
**改前 447–980ms → 改后 18/33/16/17/14ms（中位 17ms）**，案件在 1.1s 内落地，
`engine=laya:sidecar`、`state=pending`。也就是说 `MODERATION_ENABLED=true` 现在可以常开。

顺带清掉两处结构问题：

- **导入环**：`narrative_prose_text` / `project_subject_text` 从 `narrative.service`
  搬进新的 `narrative/text.py`。它们是纯投影、不碰数据库，住在 service 里会让
  "审核派发 → 取送审正文 → narrative.service → 审核派发"闭成一个环。
- **一个被自己覆盖的死方法**：`CharacterService.update_character` 在同一文件里定义了两次
  （158 与 315 行），Python 只认后一个——前一份 56 行里还有一次永远不会执行的
  `advisory_review` 调用。已删。这类"改了一份、生效的是另一份"的形状，是判断层接线时
  最容易留下的假痕迹。

测试侧必须承认这次异步化：`conftest` 每条用例结束前 `drain_pending()`。
不加会出现的是跨用例污染——上一条的判定在下一条跑到一半时落库，
实测见过一次偶发失败加一轮从 2.3s 变 33s 的套件（两条会话抢连接池）。
读队列的测试也各自显式 drain，那行代码就是在声明"我读的是最终一致的结果"。



### D13 落地：阈值假设（what-if）进队列页，顺带修掉一个"落库答案根本回放不出来"的缺陷

做这个面板的动机是把 D4 那个决定变得可核对：**具体哪几条案件会在新线下被自动执行、
它们当初人是怎么处置的**，而不是我转述的一句 `auto_rate`。开始做第一件事就是验证
"能不能用已落库的答案重放"，结果是不能：

**照出来的缺陷。** `_answer_snapshot` 写的是 `{"type","value","confidence",...}`，
而 `normalize_answers` 读的是 `{"noul"|"score"|"choice", ...}`。真机上拿一条 laya 案件回放：
**0/10 题可用，10 条违规说明**（`severity 分数不是数`、`self_harm 概率缺失或不在 [0,1]`）。
也就是说"把答案快照存下来"这件事一直是**只写不能读**的——拟合还能用（它读 `probabilities`），
但任何"用已有答案重算策略"的功能都会静默拿到一张空表，表现成"什么都没被自动执行"而不是报错。
修法是把快照写成引擎自己的形状（同一套键名），一处定义、可往返；
已入库的旧案件不写兼容分支，它们被显式跳过并给出原因：
真机 `扫描 300 · 可回放 0 · 跳过 {引擎没给类型化答案: 299, 答案回放不出来: 1}`。
旧行要点一次「让模型重判」就变成新形状。

30. **what-if 是只读的：拿已落库答案重放，不写库、不改 `Policy()`、不给任何引擎新资格。**
    每一行都带**真实生效**的那两条线（`effective_approve/reject`）。评论与素材被
    `_KIND_OVERRIDES` 收紧到 0.95/0.97，所以面板上填 0.75 不等于对评论按 0.75 判——
    这条有专门的测试，否则这个工具会教出错误的直觉。
31. **一致 / 冲突只以人工处置为准，没人判过的单独计数。** 机器要放行而人当时下架 = `conflict`
    （误放），没有处置的行不许算进一致率——`undecided` 那个数字才是自动化真正的天花板。
    读数用三态而不是布尔（`agree/conflict/undecided`；面板 tone `ok/warn/danger`），
    因为"有误放"和"缺标注"的下一步完全相反。

**这次还第一次撞见真机崩溃，而降级是按设计走的。** sidecar 在一次推理中挂在

**没有任何一条被自动执行**、后端日志留下一次失败而不是把异常抛给作者。
`引擎挂了 ≠ 内容有问题` 这条纪律从此有了真实案例。

### D14/D15 落地：引擎没答话要看得见，且降级判定不许覆盖权威结论（2026-09-27 第三轮）

起因是一次真机崩溃（MPS 断言 `MTLCommandBufferStatusCommitted`，sidecar 进程直接没了）。
当时链按设计降级了：不抛给调用方、不自动执行、词表案件照建。但事后看队列，
**中台看不出"刚才有一台引擎死了"**——D14 就是这条。查下去发现它是三处，且第二处更严重：

1. **沉默被丢了**（`engine.py` 的 `if verdict.abstained: continue`）。
   sidecar 客户端把 `URLError` 翻成 `Verdict.abstain(name, "sidecar 不可达：URLError")`，
   这句话在链里被 `continue` 扔掉，落库的案件依据只剩词表自己那几行。
   真机实录（修前，同一条案件点「让模型重判」）：
   `engine: lexicon | via: non_authoritative_engine | reasons: ["lexicon 命中 导流垃圾", …]`
   ——与"引擎活着时词表自己判的"逐字无法区分。
2. **降级判定会覆盖掉上一次的权威结论**（这条是修第 1 条时才发现的，记为 D15）。
   上面那次重判不止丢了原因，还把案件上的 `answers` / `confidence` / `clause_ids`
   换成词表的空值。修前实测：某案件 `conf 0.9844 / clauses [hate_incitement, doxxing,
   illegal_instruction]` → 点一次重判（sidecar 死着）→ `engine lexicon / conf 0.0 / clauses []`。
   后果不是"少了一行说明"：**那条内容真正的风险信号从案件上消失**，
   队列的风险排序（条款 > 置信度）还把它挪到后面，运营从此看不见它。
3. 顺带照出两处同源问题：`model_version()` 把"探测失败"按 30s TTL 缓存（sidecar 活过来之后
   最长半分钟内的真实结论仍标着 `laya:unreachable`），以及决策日志的 `engines_tried` 列
   在建案分支存引擎名、在去重分支存 reasons——同一列两种含义，复盘时分不清问了几台引擎。

改法（都很小，但每条钉死一个断言）：

| 位置 | 改动 |
| --- | --- |
| `engine.decide` | 权威引擎弃权时把原因收进 `silent`，拼到最终结论的 `reasons` 后面；同时 `logger.warning`——全链沉默时不建案件，日志是那条判定唯一的痕迹 |
| `engine.decide` | 只收权威引擎的沉默。词表在干净稿子上沉默是设计，写进去等于每条自动通过的案件都挂一行噪音，真那条被淹掉 |
| `Outcome.engine_silence` | 结构化带上"这次被问到但没答话"的清单，给服务层判"这次不如上次有资格"用 |
| `service.review` | 已有案件是权威结论、这次是降级判定时：**不动结论字段**，只在依据追加一行未答话（按内容去重，不累加） |
| `laya_sidecar` | 失败探测的 TTL 独立成 2s，成功仍 30s |
| `service.review` | 去重分支的 `engines_tried` 改回引擎名 |

修后真机同一条案件（sidecar 死着点重判）：

```
BEFORE 154973d5  engine laya:sidecar conf 0.9844 clauses [hate_incitement, doxxing, illegal_instruction] auth True
AFTER  (dead)    engine laya:sidecar conf 0.9844 clauses 同上 auth True  via human_only_clause:hate_incitement
                 依据末行「laya:sidecar 未答话：sidecar 不可达：URLError」
AFTER  (复活)    engine laya:sidecar conf 0.7871 model_state=laya:multilingual+Tddecfd30，未答话那行自动消失
```

顺带测到一条对自动化很关键的事实：**同一 payload 连打两次 `/decide`，答案逐比特相同**
（`age_rating` / `severity` / `hate_targeted` / `primary_clause` 的浮点全精度一致）。
所以"复活后置信度从 0.9844 变 0.7871"不是模型判不稳，而是 `model_state` 摘要本身变了
（`Te38e1c5c` → `Tddecfd30`，即 §12 那条标定版次失效键在起作用）。
一个诚实的缺口：`calibration.json` 不入库，我无法核对 `Te38e1c5c` 具体是哪一版表。

核验：`pytest` 134 passed（新增 6 条：引擎留痕 ×2、不污染干净稿 ×1、日志 ×1、降级不覆盖 ×1、
失败探测重试 ×1，另把原先只断言 `action` 的 sidecar-down 测试补成断依据），exit 0；
`pnpm gates` exit 0。四次变异各见过一次红，且红的是不同的测试：
去掉 `silent.append` → 3 条红；把权威筛子改成"所有弃权都记" → 干净稿那条红；
失败 TTL 也用成功 TTL → 重试那条红；`downgrade` 恒 False → 覆盖保护那条红。

仍未解（都不是代码缺口，需要口径）：
- **sidecar 自动重启**：现在死了就一路降级到人工，直到有人手工拉起。要不要给中台加"引擎进程自愈"，
  以及它算谁的职责，是产品决定。
- **MPS 崩溃根因**：`_status < MTLCommandBufferStatusCommitted` 是 torch/Metal 侧的断言，
  单实例复现一次，没有稳定触发条件。
- **判定引擎的 Python 环境寄存在未纳入版本管理的参照物里**：进程实态是
  `Clearance/vendor/laya_sidecar/.venv/bin/python backend/sidecar/server.py`。
  sidecar 代码在本仓库，但跑它的解释器和依赖树在参照物目录里——那个目录删掉，
  中台的模型判断层就起不来。该不该把它搬到 `backend/sidecar/.venv`（要重装 torch），
  也需要口径。

界面那一头在浏览器里点过了（不是只到 API 层）：真机把 sidecar 杀掉之后，
「让模型重判」的提示语读到的是
**「这台模型没答话——这次只到词表那一层：laya:sidecar 未答话：sidecar 不可达：URLError」**，
复活之后再点是 **「模型结论已更新」**；三种结果（没答话 / 命中缓存 / 结论变了）
从此各有文案。文案里"已保留上次结论"这半句是**按案件的资格状态选的**——
只有上一次的结论确实出自权威引擎时才那么说，否则说"这次只到词表那一层"，
因为词表案件被词表结论覆盖并不丢任何东西，说"保留"是假话。

> 顺带量到一个**超出审核域**的中台缺陷（记为独立任务，不在本 ADR 里修）：
> 在这条验证链上读计算样式，发现 `packages/ui` 组件里写的颜色类名在**中台的实际产物里不存在**——
> `.text-red-800` / `.bg-red-50`（Toast 的 error 变体）与 `.text-rose-300` / `.text-emerald-700`
> 在已加载的样式表里规则数为 **0**，toast 元素的 `color` 计算值是 `rgb(31,41,55)`（就是墨色），
> 而中台自己 src 里写过的类（`bg-surface`、`bg-rose-500/15`）都正常解析。
> 也就是说**成功与失败提示目前在视觉上完全同款**，Badge 的文字色同理失效。
> 判据是"计算样式 + 规则数"两条一起量的，不是 grep 类名字符串——
> `.bg-rose-50` 会被 `.bg-rose-500/15` 的子串匹配骗过第一次。
> 这件事的修法会一次性给整个中台换上一批从没生效过的颜色，属于视觉层的地基改动，
> 需要单独一轮（含对比度门禁的配对登记），不要顺手做。

### D16 落地：what-if 的读数要连着样本量说（顺带把窗口默认改成覆盖全库）

`/what-if` 此前默认只读**最新 500 条**案件，而响应里没有"全库多少条"这个数。
真机量：库里 **979 条**案件，所以那句"这条线只会自动执行 3 条"实际意思是
"在我看得见的 500 条里 3 条"，另外 **479 条（49%）在界面上等于不存在**——
与 D12 分页那一轮是同一课（`limit` 就是硬上限）。

改三处，都很小：

| 改动 | 理由 |
| --- | --- |
| 响应加 `population`（同一张表的行数，端点测试里与直接 `count(*)` 比对，不是猜的） | 截断与读数必须在同一屏说 |
| `scan` 默认 **500 → 2000**，上限 2000 → 5000 | 实测读全量 979 条 **~10ms**，与读 500 条（6–46ms）无差别，没有性能理由留着半截证据 |
| 服务层 `scan` 改为**必填** | 默认值只许在路由那一处声明；两处各写一份就是双真相源，改一忘一时窗宽静默变化 |

面板那条读数现在是「扫描 979 条案件，可回放 6 条」（`scanned < population` 时才追加
"全库 N 条，这里只取最新 M 条"）。

**同一个数当时其实在三处各写了一份**：路由 `Query(default=500)`、服务层 `scan: int = 500`、
前端 `moderationWhatIf(approve, reject, scan = 500)`。第三条是浏览器里量出来的——
把服务层默认改掉之后面板仍显示"扫描 500 条"，才顺着查到客户端也带了一份。
现在三处收成一个：只有路由那一份默认值，服务层 `scan` 改必填，前端参数改可选透传。
修完面板真机读数变成「扫描 994 条案件，可回放 6 条 … 跳过：引擎没给类型化答案 977、
答案回放不出来 11」（不再截断，所以尾巴里的"全库…"整句消失，这条也在浏览器里点过）。
两次读数差的 15 条是这期间后台判定继续落库，不是同一个数变了口径。

顺带把 D4 的真瓶颈量清楚了：**979 条里只有 6 条带可回放的类型化答案**。
所以"要不要把通过线从 0.90 挪到 0.75"这个决定，缺的从来不是窗口大小
（500 与 2000 两档下 `evaluated` 都是 6、`conflicts` 都是 0、`undecided` 都是 6），
而是**带机器答案的案件太少**——绝大多数案件是词表判的，本来就没有向量可重放。
这把 §"还差什么"里"攒标注"那一步的口径钉得更准：要攒的是**走完了模型那一层的案件**。

核验：`pytest` 134 passed（端点测试补 3 条断言：`scanned==1`、`population==直接 count`、
`population>=scanned`），把 `population` 去掉那次变异只打红这一条；
`vitest` 18 passed（新增样本量两条，`return ""` 那次变异只打红正向那条）；`pnpm gates` exit 0。


### D17 落地：队列结论的"版本新鲜度"要看得见（2026-09-28 第四轮）

顺着 D16 那句"只有 6 条带可回放答案"往下量，得到的分布比预想的更值得说：

| 实测（dev 库，994→1009 条案件） | 数 |
| --- | --- |
| 结论是在**旧题集**（`questions-2`，即 D3 加单选题之前）上判的 | **264** |
| 结论挂着**旧词表**版本号（`lexicon-1`） | **111** |
| 结论**不是权威引擎给的**（词表判的或全体弃权，即从未走到 Laya） | **977 / 992** |
| 真正带类型化答案、可被 what-if 重放的 | **17**（what-if 里 6 条落在窗口内） |
| 状态分布 | pending 100%，即**没有一条被自动执行过** |

这组数说明两件此前在界面上完全看不见的事：

1. **判定只在内容保存那一刻发生，改版不会自己回头重算。** §12 的幂等键保证了"重新送审必然重算"，
   但没人触发就没人重算——264 条结论今天仍坐在旧题集的判断基础上。
2. **"自动判断到底覆盖了多少内容"的真分母不是 `auto_rate`，而是"有几条走到了模型那一层"。**
   977/994 只有词表判过，这一环在 `auto_rate=0` 的读数里是完全隐形的。

因此 `GET /stats` 新增 `staleness`（`total / stale_questions / stale_lexicon / without_authoritative_verdict`
+ 当前两个版本号），队列页顶部多一枚 chip：
真机读数 **「版本已推进但结论没重算：264 条是 questions-3 之前的题集判的、111 条挂着旧词表版本」**。
`without_authoritative_verdict` 先只进 API 不上界面——它和 `by_engine`（lexicon 975 / laya 17）
是同一事实的两种问法，界面重复一处就会长出漂移。

**没做的事，以及为什么**：这一轮**没有**加"批量重判"。它看起来是这条链的自然下一步
（点一下就把 264 条旧结论刷新），但重判走的是同一道门控，一旦某条新结论越过阈值，
它就是**第一次由机器执行的不可逆动作**，而且是在无人逐条看过的 264 条上同时发生。
这一步要先有口径：批量重判是否默认只刷新建议、不许改变执行状态；以及谁批准第一次批量执行。
`staleness` 就是为那个决定准备的读数。

核验：`pytest` 135 passed（新增 1 条，用**增量**断言避开 dev 库上别的写者，并在序列前 `drain_pending()`；
把 `stale_questions` 写死成 0 的那次变异只打红这一条）；`vitest` 20 passed（新增 2 条，
去掉 `parts.push` 那次变异只打红正向那条）；admin `tsc` 0 error；`pnpm gates` exit 0；
chip 在真浏览器里读到的是上面那句原文。

### 现在到"真的自动"之间还差什么

按顺序，且第 2 步之前不要谈自动化率：

1. 起后端与 sidecar（`MODERATION_ENABLED=true`），让判断层以**建议**身份跑一段，攒案件与处置。
   此刻这条链已经能在真机上判全文并留痕，`auto_rate` 是 0，但每一案都有可读的"为什么没自动"。
2. `eval/export_labels.py` 导出「带类型化答案 + 已人工结案」的标注（现在会顺带报告
   其中多少条带概率向量——不带向量的旧案件只能重拟二元轴），`eval/calibrate.py` 重拟。
   只有 **10/10 题**（questions-3 加了 `primary_clause`）都被覆盖，客户端才认为整链已标定；
   部分标定一律转人工。
3. 把 34 行单人标注集升级成多人一致金集。在那之前，本 ADR 的所有准确率数字
   只能说明"实现与策略自洽、失败时安全"，不能对外宣称模型效果。
4. 词表外置为可热更配置；`report` 队列与本队列的联动。

第 2 步有先有鸡还是先有蛋的性质，而且这一轮把它测准了：**蛋（标注）只能从"纯建议模式"的人工处置里来，
而鸡（标定表）在拿到真实标注之前拟合出来的任何自动化率都是自证的**。

**这一轮还更正了本 ADR 先前的一句话。** 我写过"后半句的开关是标注量，不是代码"——
一半对，一半不对：温度缩放无法表达稀有事件的先验（见 D10），这部分**就是代码**，
而它当时正在压低 `auto_rate`。修掉之后同一份 34 行标注下的安全前沿从 1 条变成 3 条（0.75 线，零误放）。
所以此刻剩下的分岔是三件事，不是两件：
**(a)** 标注量与多人一致金集；**(b)** `severity` 这条轴目前没有区分力
（顶档概率最高的是干净内容，34 行里无一越过 0.5）——D11 已经不再让它误否决，
但它该不该有否决权，要等它证明自己读得懂；**(c)** 一条产品决策：
通过线要不要从 0.90 落到 0.75——(a) 没做完之前，这个决定的证据仍然只有单人标注的 34 行。
