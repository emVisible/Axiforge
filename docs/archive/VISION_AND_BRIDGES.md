# Axiforge 北极星与桥梁架构（Vision & Bridges）

> **文档性质**：终极愿景 + 支撑愿景的地基架构（"桥梁"），是 `ROADMAP_vNEXT.md` 的**上位文档**。
> **最后更新**：2026-07-07
> **一句话**：`ROADMAP_vNEXT` 定义"里程碑的节奏"（做透、可 ship）；本文定义"每一步该往哪座桥上落"（不返工、能通向北极星）。

---

## 0. 为什么要有这份文档

`ROADMAP_vNEXT.md` 是一条**克制的直线**：先把现有的四条产品线（Character / Script / Asset / Lite Player）打磨发布，AI / Unity / 演出 / 世界 tick 全部推迟。这在"避免头重脚轻"上是对的。

但它与你的**北极星**存在结构性冲突：

> 终极愿景 = 取代**高级** Visual Novel 制作 Studio + Runtime，让普通创作者简便舒适地做出**明日方舟 / 命运石之门**级别的作品；覆盖 VN 全维度，且带有你独特的创新点 **RN**。

明日方舟、命运石之门的价值，**80% 在"演出（Direction）"与"系统层"**——镜头、立绘差分、全语音、转场、世界线/手机短信系统、存档/图鉴/术语库。而现路线把这些定义性能力全部推到了 v2.5 的 Unity 才碰。等于**把桥全修在浅滩，深水区留到最后重来**。

本文不推翻"小步交付"，而是回答一个更关键的问题：

> **哪几步应该修成"桥"（可复用的地基），哪几步可以继续走"直线"（一次性的功能）？**

选错了，Lite Player 越 polish 越是给"注定要重写的东西镀金"（sunk cost）；选对了，同一份地基能同时喂养 Lite Player、未来的高保真 Runtime、离线导出、Unity，甚至 UGC 二创。

## 1. 北极星：两个身份，一条护城河

Axiforge 要同时是两样东西：

| 身份 | 含义 | 对标 | 衡量标准 |
|------|------|------|----------|
| **VN 全维度平台** | 传统 VN 引擎能做的，我们都要能做，且更好做 | Ren'Py / TyranoBuilder / Naninovel / 吉里吉里 | 一个专业 VN 团队愿意放弃现有引擎迁过来 |
| **RN 创新平台** | 传统引擎**做不到**的关系/记忆/IP 维度 | 无直接对标（这是护城河） | 创作者因为 RN 而无法离开 |

### RN 到底是什么（把它讲死）

**RN = Relational / Relational-Nova：以"关系与记忆"为一等公民的叙事范式。**

传统 VN 里，"角色"是某个作品内部的贴图 + 一堆 flag，作品结束即消失。RN 把这个假设整个掀翻：

1. **角色即 IP 资产（Character-as-IP）** — 角色活在任何单一剧本**之外**，可跨作品复用。（现已有雏形：`characters` 表 + 六层模型 + Fork）
2. **关系持续（Persistent Relationship）** — 角色之间、角色与玩家之间的关系是**可查询、可累积、可跨作品继承**的实体，而非临时 flag。
3. **记忆驱动分支（Memory-driven Branching）** — 分支由"累积的记忆/状态"决定，而不是纯分支树；记忆可跨会话、（长期）跨作品。
4. **世界可演化（Evolving World）** — 世界线、时间、关系可以被规则或（远期）AI 自主推进——这是命运石之门"世界线变动率"的底层能力。

> **一句话记住**：别人做的是"一部作品"，我们让创作者经营的是"一个会记事、会长大、能跨作品出演的角色宇宙"。这就是普通 VN Studio 给不了的东西。

## 3. 现状诚实诊断（问题与"不合适"）

按"越靠地基越致命"排序。每条都附代码证据。

### 3.1 【地基级·最致命】没有"演出脚本"这一层——节点粒度错了

```135:171:backend/app/models/project.py
class ProjectNode(Base):
    # narrative_data: { title, description, speaker, dialogue, narration,
    #                   trigger_condition, effects, choices, auto_advance }
```

一个图节点 = **一句** speaker+dialogue（+可选 choices）。但真实 VN 的一个"场景"是**几十到上百条演出指令**的序列：进场→表情变→镜头推近→BGM 变→说话→SE→退场……

**后果**：

- 想做一段像样的演出，得在图里拖几十个节点连成一条线——创作者体验灾难，与"简便舒适"完全相反。
- 立绘、镜头、音频**没有任何模型承载**，只能塞进对话文本或临时字段。
- 这是 D2/D3 全空白的**根因**，不是"还没做"，而是"数据模型里没有它的位置"。

> **不合适的本质**：把"宏观流程图（Flow）"和"微观演出脚本（Script）"压成了同一层。高级 VN 必须是**两层**：Flow 管"哪个场景接哪个场景/分支"，Script 管"一个场景内怎么演"。

### 3.2 【地基级】运行时是"每句话一次网络往返"，且逻辑焊死在后端

```30:39:backend/app/services/player.py
class PlayerService:
    """玩家运行时服务——叙事状态机"""
```

`draw` / `complete` 每推进一个节点就打一次 API，条件评估、效果应用全在 Python 端 (`_evaluate_condition` / `_apply_effects`)。

**后果**：

- 聊天式往返，无法做流畅演出（演出需要客户端连续播放时间轴，不是一句一请求）。
- **无法离线、无法打包、无法导出**——D10 直接被架构堵死。
- 未来 Unity / 高保真 Runtime 要复用逻辑时，得把 Python 里的状态机**重写一遍**（现路线 v2.5 正是这么打算的）。

### 3.3 【地基级】承诺的 DSL 引擎（`core/` `shared/`）在磁盘上根本不存在

`REFACTOR_PLAN` 反复提到"`core/shared` 保留、为 v1.5 `.rn`/Unity 预留"，但实际仓库里**没有这两个目录**，`pnpm-workspace.yaml` 也不含它们。条件/效果逻辑三处分散、互不共享：

- 编辑器：`ProjectFlowPage.tsx`（~1447 行，`ConditionEditor`/`EffectEditor`）
- 运行时：`backend/app/services/player.py`（`_evaluate_condition`）
- 存储：`project_nodes.narrative_data` 散装 JSONB

**后果**：条件语义**不可共享、不可单测、不可版本化**。改一处要手动同步三处，是长期一致性地雷。这正是 RN"记忆驱动"要立足的地方，却建在流沙上。

### 3.4 【RN 护城河级】记忆是"会话级"的，撑不起"关系持续 / 跨作品"

`runtime_sessions` / `session_memories` / `session_flags` / `character_runtime_states` 全部挂在**单次会话**下，玩完即弃。

**后果**：RN 的核心承诺——"角色记得玩家、关系跨作品继承"——**没有任何持久层可落脚**。现路线 v1.2 的"记忆驱动"仍是会话内 flag 分支，这不是 RN，是每个 VN 引擎都有的普通 flag。**护城河没开始挖。**

### 3.5 【体验级】Lite Player 是 704 行硬编码巨石，且是唯一 Runtime

`PlayerPage.tsx` 把打字机、分支、HUD、立绘、结束页全焊在一个组件里，不是"消费某种 IR 的渲染器"。现路线把大量 v1.x 预算投入"打磨 Lite Player"，但它没架在演出 IR 上——**polish 得越多，将来重写时扔掉的越多**。

### 3.6 【工程级】死代码暴露了"曾经想对、后来砍掉"的更好模型

- `models/world.py`（`WorldScene`/`WorldSceneNode`，含 `trigger_condition`/`effects`）**未注册、无路由、不建表**——这是一个被放弃的、其实指向"世界可演化(D7/D8)"的更丰富模型。
- `models/item.py`、`models/memory.py` 同为死代码。

**后果**：不仅是垃圾待清，更说明**曾有更大的构想被"直线原则"砍掉了**。这次要把其中对的部分（世界/时间/持久记忆）以正确的架构方式接回来。

### 3.7 【工程级】其它

| 项 | 证据 | 影响 |
|----|------|------|
| 编辑器巨石 | `ProjectFlowPage.tsx` ~1447 行、单 `StoryNode` 类型 | 演出/多节点类型无法扩展 |
| 无玩家身份 | `author_id="anonymous"` 全局 | RN"角色记得玩家"无主体 |
| 测试极薄 | 仅 3 个后端集成测试，无前端/无引擎测试 | 引擎重构无安全网 |
| 无资产管线 | `asset_items`/`asset_scenes` 仅元数据 | D9 全空白 |
| bundle 未拆分 | ~766KB | 加了演出/资产后会更糟 |

### 3.8 对现有 `ROADMAP_vNEXT` 的元评价

它没有错，它只是**把"深度"等同于"把薄的东西打磨光滑"**。真正的深度是**把地基换厚**。三条具体分歧：

1. **"Lite Player 做好 = 体验终点"** 过度简化。体验终点是"演出质量"，而演出质量取决于是否有演出 IR/引擎，不取决于给现有文本框加多少动画。
2. **把 D2/D3/D5/D9/D10（演出/音频/系统/资产/发布）整体推到 Unity 时代**，等于把"高级 VN"的定义性能力全部延后，中间产物无法验证北极星。
3. **v1.2 的"记忆驱动"名不副实**——它是会话 flag，不是 RN 持久记忆。护城河命名了却没开挖。

> 澄清：defer **AI 节点 / 世界自动 tick** 是对的克制（那是消费者未就绪的能力）。但 defer **演出 IR / 统一表达式 / 持久关系 / 资产管线**是把"核心体验和护城河"也 defer 了——这才是要纠正的。

## 4. 七座桥（支撑北极星的地基架构）

"建桥搭路"的具体含义：下面 7 项是**可复用的地基抽象**，一旦建好，后续每个功能都是往桥上加一跨，而不是重新架桥。每座桥都标注了**最小可用形态（MVP 跨度）**——桥要早建，但可以先建独木桥再加宽。

```
        北极星：取代高级 VN Studio + Runtime（VN 全维度 + RN 护城河）
   ┌───────────────────────────────────────────────────────────────┐
   │  桥7 玩家身份 & UGC 层                                           │
   ├───────────────────────────────────────────────────────────────┤
   │  桥4 角色 IP / 关系 / 记忆账本（RN 护城河）                       │
   ├──────────────────────┬────────────────────────────────────────┤
   │  桥5 资产管线          │  桥6 Runtime 系统层（存档/图鉴/设定/术语）│
   ├──────────────────────┴────────────────────────────────────────┤
   │  桥2 演出指令时间轴（Direction Timeline）  ← VN 的本体            │
   ├───────────────────────────────────────────────────────────────┤
   │  桥3 统一表达式/条件系统（.rn 语义核心）                          │
   ├───────────────────────────────────────────────────────────────┤
   │  桥1 叙事 IR + Story Compiler（脊椎：编译成可移植故事包）          │
   └───────────────────────────────────────────────────────────────┘
```

### 桥1 —— 叙事 IR + Story Compiler（脊椎）

**解决**：3.2（服务器焊死）、3.5（巨石 Player）、D10（发布形态）。

**是什么**：定义一套**与渲染端无关的中间表示（Narrative IR）**——把"一个项目"编译成一份**可移植的 Story Package**（编译后的指令流 + 资产清单 + 起始状态）。后端从"逐句解释器"退化为"**编译器 + 持久化**"；播放端（Lite Player / 未来 Unity / 离线包）从"每句请求"变成"**加载包后本地推进**"。

**为什么现在建**：这是让"Lite Player polish 不白费"的唯一办法——Lite Player 变成"IR 的第一个渲染器"，同一 IR 未来喂 Unity、离线导出、二创。**这一根脊椎决定了后面所有桥能不能复用。**

**MVP 跨度**：先定义 IR 的 TypeScript/Python 双端 schema（放进真正落地的 `packages/core`），把现有 `player.py` 的推进逻辑改写成"编译 project → IR"，Lite Player 改成读 IR 本地推进。后端只保留：编译、存档同步、（含私密条件的）服务端裁决。

**最终形态**：`project → compile → StoryPackage(.axsp)` 可下载、可离线、可导入 Unity。

### 桥2 —— 演出指令时间轴（Direction Timeline）

**解决**：3.1（节点粒度错）、D2、D3、D4。这是**最能直接对标明日方舟/命运石之门**的一座桥。

**是什么**：在 Flow（宏观图）和 Player 之间插入**演出脚本层**。一个"场景/节点"内部是一串**有序、可并行的演出指令**：

```
say(char, "台词", voice?) / show(char, expr, pos) / hide(char, transition)
move(char, to, ease) / bg(image, transition) / cg(image) / camera(zoom|pan|shake)
bgm(track, fade) / se(sound) / wait(ms) / fx(rain|snow|flash) / choice([...]) / branch(...)
```

编辑器侧配套**时间轴/剧本式演出编辑器**（不是拖几十个图节点），支持"边写边预览"。这层直接编译进桥1 的 IR。

**为什么现在建**：D2 的空白是**数据模型缺位**造成的（3.1），越晚建，Lite Player 里硬编码的临时演出字段越多、迁移越痛。**指令集是 VN 的"字节码"，定义得早，创作与运行时同时受益。**

**MVP 跨度**：先支持 `say/show/hide/bg/bgm/se/wait/choice` 8 条指令 + 一个线性演出编辑器；镜头/特效/Live2D 逐版本加指令，不改架构。

### 桥3 —— 统一表达式 / 条件系统（.rn 语义核心）

**解决**：3.3（三处分散）、D8 的语义基础。

**是什么**：一套**前后端共享、可单测、可版本化**的条件/效果/表达式定义（typed schema + 求值器），放进 `packages/core`。编辑器、编译器、运行时、（远期）Unity **共用同一份**。这就是 `.rn` DSL 的语义内核（DSL 只是它的文本语法糖，可后置）。

**为什么现在建**：记忆驱动（桥4）、限时选项/世界线（D6/D7）全都依赖"条件"这门语言。现在建，后面所有条件相关功能零重复。

**MVP 跨度**：先把现有 4 种条件（memory/flag/character_state/node_completed）抽成共享 schema + 双端求值器 + 一个"条件模拟器"，替换掉 `player.py` 与 `ProjectFlowPage.tsx` 里的重复实现。

### 桥4 —— 角色 IP / 关系 / 记忆账本（RN 护城河）

**解决**：3.4（记忆仅会话级）、D8。**这是唯一别人抄不走的桥。**

**是什么**：把"记忆/关系"从会话级提升为**持久实体**，分三层：

| 层 | 作用域 | 例子 |
|----|--------|------|
| **会话记忆** | 单次游玩 | 本局选了什么（已有） |
| **存档记忆** | 一份存档/一次通关 | 某路线的关系值（桥6 存档接入） |
| **IP 账本（Codex）** | 跨作品、绑玩家身份 | "这个角色记得你在上一部作品救过她" |

配套**关系账本**（角色↔角色、角色↔玩家的持续关系边，可累积、可被条件查询、可被下一部作品继承）。

**为什么现在建**：这是产品的**存在理由**。可以晚"做大"，但**数据模型的分层现在就要定**，否则会话级设计会像藤蔓一样长满代码，日后拆解成本极高（正如现在的 `world.py` 死代码所示）。

**MVP 跨度**：先落"存档记忆"层 + 玩家身份占位（桥7），让关系值能跨会话存活；跨作品继承作为 opt-in 的 v2 能力。

### 桥5 —— 资产管线（Asset Pipeline）

**解决**：D9。演出的血肉。

**是什么**：立绘 / 表情差分 / 背景 / CG / BGM / SE / 语音 /（远期 Live2D、视频）的**导入 → 管理 → 优化（图集/多分辨率/压缩）→ 引用**。与桥2 指令直接挂钩（`show(char, expr)` 的 `expr` 指向差分资产）。

**为什么现在建**：`asset_items`/`asset_scenes` 现在只是元数据，加演出前必须有真素材承载。**MVP 可以只做"上传+分类+引用"**，图集/优化后置——但引用模型要一次定对。

### 桥6 —— Runtime 系统层（存档 / 图鉴 / 设定 / 术语 / 设置）

**解决**：D5、D7。"取代 Runtime"的入场券。

**是什么**：VN 的"外壳系统"：多槽存档/读档（带缩略图与摘要）、设置（文字速度/音量/自动语速）、CG 鉴赏、音乐鉴赏、剧情回顾、**术语库/tips**（命运石之门名词解释）、**角色图鉴/档案**（明日方舟干员档案）、**世界线/时间线视图**（把 `world.py` 想做的东西正确地接回来）。

**为什么现在建**：存档层是桥4"存档记忆"的落点；设定/术语/图鉴是桥5 资产与桥4 IP 的自然消费者。不必一次做全，但**存档要早**（否则演出做出来了却存不下）。

### 桥7 —— 玩家身份 & UGC 层

**解决**：3.4 缺主体、UGC 平台化。

**是什么**：轻量玩家/创作者身份（RN"角色记得**你**"的主体），之上叠 UGC（发布/发现/Fork/二创/播放计数）。UGC 是**放大器**，位置在最上层，设计提前留、实现最后做——这一点与现路线一致，予以保留。

**MVP 跨度**：先做"匿名可迁移的本地身份"→ 简易 auth → UGC。不阻塞创作与演出。

## 5. 重排版本路线（桥梁优先，但仍小步可 ship）

核心原则改为：**每个版本必须"加厚一根地基"，同时"交付一个可感知的作品级提升"。** 不再是"先把薄的打磨完再谈深的"。

> 与 `ROADMAP_vNEXT` 的关系：本节**替换**其 §5 的里程碑排序；其"做透验收标准""UGC 顺序克制""不做 AI/tick"等原则**全部保留**。

### v1.1 「脊椎与演出雏形」——建桥1 + 桥2 独木桥

- 落地 `packages/core`（真实存在！）：定义 **Narrative IR** + **演出指令集 v0**（8 条指令）。
- 后端 `player.py` 重构为 **project → IR 编译器**；Lite Player 改为 **IR 渲染器**（本地推进，不再每句请求）。
- Flow 之下引入**场景演出脚本层**（线性演出编辑器 MVP）。
- **可感知提升**：一个场景能连续演出"进场→变表情→切 BGM→对话→选择"，而不是拖 5 个图节点。
- 验收：同一份 IR 同时驱动 Lite Player 与一个 headless 测试跑通；演出脚本可保存可回放。

### v1.2 「记忆驱动·真」——建桥3 + 桥4 独木桥

- 抽出**统一表达式/条件系统**到 `packages/core`，前后端共用，删除三处重复；提供条件模拟器。
- 记忆分层：新增**存档记忆层**（跨会话存活），关系值不再玩完即弃。
- **可感知提升**：分支真正由"累积关系/记忆"驱动，且**下次进来角色还记得**。
- 验收：条件系统单测覆盖；同一条件在编辑器模拟、编译、运行时三处行为一致。

### v1.3 「演出加宽 + 资产管线」——加宽桥2 + 建桥5

- 演出指令扩到镜头（推拉摇移/震动）、转场、特效、旁白富文本、ruby。
- 资产管线 MVP：立绘/差分/背景/BGM/SE/语音 的导入·分类·引用；演出编辑器可选素材边写边预览。
- **可感知提升**：能做出一段"有镜头语言 + 配乐 + 语音"的明日方舟风格演出。
- 验收：一段 ≥30 秒的高质量演出，纯用编辑器产出，无需写代码。

### v1.4 「系统层 + 存档」——建桥6

- 多槽存档/读档（缩略图+摘要）、设置面板、backlog+语音回放、CG/音乐鉴赏、术语库、角色图鉴。
- 把 `world.py` 的意图**正确接回**：世界线/时间线视图（只读展示，先不 tick）。
- **可感知提升**：作品可以"关掉再回来继续"、有鉴赏和设定库——像成品而非 demo。
- 验收：完整一周目 → 存档 → 关闭 → 读档续玩 → 解锁 CG 进鉴赏。

### v1.5 「玩家身份 + UGC 最小平台」——建桥7

- 可迁移玩家身份 + 简易 auth；公开/发现/Fork/二创/播放计数。
- **RN 首次跨作品**：角色 IP 账本 opt-in，允许"角色带着上一部的记忆"进入新作品（护城河首秀）。
- 验收：新用户浏览 → 玩 → Fork 角色 → 该角色在新剧本里保留关系记忆。

### v2.0+ 「高保真 Runtime + 世界演化 + AI」（远期，仍只规划）

- 因为桥1 已产出可移植 IR，**Unity/高保真 Runtime 是"再写一个 IR 渲染器"，不是重写引擎**。
- 世界 tick / AI 节点：此时消费者（演出、记忆、关系）已就绪，AI 落在成熟地基上，而非掩盖工具短板。
- Live2D / 视频 / 本地化 / 商店发行。

> 节奏对比：现路线 v1.1–v1.5 = 打磨 4 条现有产品线；新路线 v1.1–v1.5 = **每版加厚一根桥 + 交付一个作品级能力**，v2.0 的 Unity 从"重写"变成"复用"。

## 7. 不变的克制（避免另一种头重脚轻）

"建桥"不等于"一次性把七座桥全建成高速公路"。纪律：

1. **桥要早建，但先建独木桥**：每座桥的 MVP 跨度已在 §4 标注，先窄后宽。
2. **AI / 世界自动 tick 仍后置**：它们是"地基的消费者"，地基（演出/记忆/关系）没铺好之前上 AI，只会掩盖短板——这一条与 `ROADMAP_vNEXT` 完全一致。
3. **每版仍要可 ship**：桥梁优先不豁免"做透"验收标准（Empty/Error/Loading、集成测试、30 分钟 happy path）。
4. **UGC 仍最后加壳**：桥7 在最上层，设计提前留、实现最后做。
5. **不为架构而架构**：每座桥都必须对应能力地图（§2）里一个具体的 VN/RN 维度，否则不建。
