## v2.5 已交付：审核判断层（运营视角）

机器结论出现在两个地方，都不是新闸门：

- **审核工作台右侧**「自动判断」条：动作 + 依据（`via` 展开成中文）+ 命中条款 +
  「有执行资格 / 未校准」标记。带虚线框的那枚是**模型建议**（单选"最主要一条"），
  只递到人眼前，不参与任何执行。
- **自动判断队列页**：同一份结论按案件列出来，默认「先看可疑」——按命中条款严重度、
  再看置信度排序。排序不是结论，它只决定谁先看。

两页都能翻页，底部显示「第 x–y 条 · 共 N 条」。这个数字很要紧：此前 `limit` 就是硬上限，
举报列表只显示前 50 条而 pending 有 197 条——看不见的举报不是"排在后面"，是没有入口。

队列页底部有一块**阈值假设**（只读）：填两条假定的线，面板回给你"这 N 条已处置过的案件里
会有几条被自动执行、其中几条与当时的人工结论相反"。它不改策略、不写库，
每一行还会显示**该类型真实生效**的那条线（评论/素材收紧到 0.95/0.97，
所以填 0.75 不等于对评论按 0.75 判）。读数分三种：有误放（红）、会自动执行但缺人工对照（黄）、
与人工一致或什么都不执行（绿）。
读数条同时写明这份证据的**基数**：「扫描 979 条案件，可回放 6 条」——默认窗口已覆盖全库，
真被截断时会追加「全库 N 条，这里只取最新 M 条」，因为"只影响 3 条"和
"在我看得见的这些里影响 3 条"是两个不同的数。注意**可回放**那一项通常远小于扫描数：
只有走过模型那一层的案件才带着可重放的类型化答案，词表判的那些没有向量。
而且**可回放的案件数也不是样本量**——读数会紧跟一句「不同内容仅 24 篇，重复文本不增加样本量」：
同一段稿子被反复保存会产生很多案件，但对"这条线安不安全"这个判断只算一条证据。

处置理由旁边有一个**逐轴真值**开关：勾上「我逐轴核对过这条内容的条款真值」才会出现一排条款，
点选的中文条款名就是这次处置认定的真值。两个"空"完全不同，别弄混：
**不勾**＝"我没逐轴看过"（导出沿用机器标的条款）；**勾了但一条都不选**＝"机器报的条款一个都不成立"
（那是标定数据里最值钱的负样本）。处置完成后控件会自动清空——不然下一行会被这条没读过的勾选污染。
为什么值得多这一下：温度表是用这些标签拟出来的，而机器不会报告自己漏掉的东西——
没有逐轴勾选，"人觉得有、机器没报"的那类样本永远是 0，拟出的温度就会偏乐观，
门控看起来就会比实际更该放松。

可以点的动作：
| 动作 | 含义 |
|------|------|
| 让模型重判 | 取**全文**（作品 = 简介 + 旁白台词；评论 = 完整正文）现在判一次。内容与策略版本都没变时命中指纹缓存：结论不动，只多一行判断记录，提示语会区分这两种结果。**模型没答话时不覆盖旧结论**：sidecar 死了就点重判，案件保持上一次模型给的条款与置信度，依据里多一行「laya:sidecar 未答话：…」——降级的那次判定没有资格把风险信号抹掉 |
| 确认处置 / 回退 | 人的判断落库并写入审计日志；终态可以回退成待处理（误判要有回去的路） |
| 驳回举报 / 下架内容 | 下架会记违规并累计 strike；重判不会替你做这两步里的任何一步 |

队列页底部还有一块**批量重判**（`ModerationRequeuePanel`）：选范围（模型没答过的 / 版本已推进的 /
全部待处置）、填最多判几条、启动，进度徽章 1.2s 一跳。两条写死的设计：

- **默认不结案**。勾选框叫「允许批量结案（会把过门的移出待处置）」，不勾时结论照刷新、案件仍留在
  人工队列里 —— 攒标定证据不需要清空人的视野，而"这些不用看了"必须是人说的一句话。
- **读数不许把"只有词表说话"算成判完**。面板上 `模型答了 N 条 · M 条只有词表说话` 里
  只要 M>0 或 N=0 就是黄的、有失败就是红的，不会假绿。
  真机两条都走过：模型活着时绿底「模型答了 5 条 · 3 条原内容已不在」；
  把 sidecar 杀掉再跑一次，同一位置变成琥珀底「模型答了 0 条 · **3 条只有词表说话** · 3 条原内容已不在」。

一轮跑完会自己把队列与统计重新取数（轮询必须能取到"跑完了"那一次快照——
一开始挂在 react-query 的 `refetchInterval` 上时，面板会停在「重判中 0/200」而服务端早已结束）。

自动化开关的现状：默认 `MODERATION_ENABLED=false`，链里只有词表且它没有执行资格；
打开 Laya 后模型有执行资格，但放行/驳回线（0.90 / 0.95）是扫阈值扫出来的，
未标定的题只要有一题没覆盖就一律转人工。判据口径与实测数字都在
[ADR-028](./ADR/028-moderation-decision-layer-in-admin.md)。

打开 Laya 不再是作者的代价：评论、角色公开、作品保存的判定都挪到了后台
（真机改一次正文的保存耗时 447–980ms → 14–33ms），案件通常在 1–2 秒内出现在队列里。
举报是唯一保持同步的入口——运营打开一条举报时屏上就该有结论，那一次等待是买这笔信息的钱。
也因此队列是**最终一致**的：刚保存的内容短暂地"还没被机器看过"是正常状态，不是丢单。

界面上出现的每一个条款名、规则名、结论名、问题名都来自 `GET /admin/moderation/vocabulary`——
后端在定义它们的那几个模块旁边各放了一份短名，导入期断言与取值域逐项相等。
所以加一条新条款不需要改前端；反过来说，如果哪天你在队列里看到 `spam_promotion`
这样的内部 id，那是词汇表接口出问题了，不是文案没来得及改。

队列页头部常驻四枚状态条，用来回答"为什么没有东西被自动处置"：引擎在线与是否有执行资格、
**温度表覆盖面**、当前策略的通过线/驳回线、**队列结论的版本新鲜度**。覆盖面那一枚分三种读法：
缺哪几题（黄）、取不到标定状态（红）、题数齐但**拟合触到搜索网格上限**（黄）。
最后一种最容易被读成"标定完成了"——它的意思其实是"这几题的置信度还虚高，只是压不到线下"，
所以它不复用全绿的外观。题目名字来自词汇表，界面不会出现 `pii_real_person` 这种内部字段名。

第四枚说的是一件很容易忽略的事：**判定只在内容被保存那一刻发生**，题集或词表改版**不会自己回头
重算**。所以「待处置 994 条」并不等于「994 条同等新鲜的证据」——真机读数就是
「版本已推进但结论没重算：264 条是 questions-3 之前的题集判的、111 条挂着旧词表版本」，
意思是这些行要让结论变新鲜，只能逐条点「让模型重判」（或等批量重判那条路定下来）。

**运营处置怎么变成温度表**（这条路已经通了，缺的只是量）：每次「确认处置 / 误报」都在给
当时那份类型化答案打真实标签。命令行两步，`backend/` 下跑：

```
uv run python eval/export_labels.py --out eval/moderation_labels.jsonl
uv run python eval/calibrate.py --from-answers eval/moderation_labels.jsonl --out /tmp/试拟.json
```

导出会逐轴报「可拟样本 / 正样本」并对三种致命形状报警（一条都拟不动 / 只有负样本 / 只有正样本）；
`--from-answers` 用的是**缩放前**那份分布（案件快照里现在同时存了缩放后与缩放前两份，
真机同一条 `sexual_content` 是 0.177 与 0.502），所以在已缩放的分布上再缩一次的错误口径不可能发生。
样本不够时它**不写表**并说明原因——空表比假表好，门控据此继续转人工。
验证性重拟请一律带 `--out /tmp/…`，别覆盖在线加载的那张表。

## v2.5 补：中台的组件颜色此前从未生效（2026-09-28 修）

**现象**：中台里"成功"和"失败"的浮层提示长得一模一样，Badge 只有底色没有文字色。
**根因**：Tailwind v4 只生成**扫得到的源里出现过的**类名。`apps/web/src/index.css` 有
`@source "../../../packages/ui/src";`，`apps/admin/src/index.css` 没有——于是
`packages/ui` 组件里写的色板类名在中台产物里**规则数为 0**。探针实测（注入类名读计算样式）：
`bg-red-50` / `text-red-800` / `text-rose-300` / `text-emerald-700` 全部透明底 + 继承墨色；
而中台自己 src 里写过的 `bg-surface`、`bg-rose-500/15` 正常解析。构建、lint、单测全绿，
没有任何一处会报——这类缺陷只能靠"在产物层读计算值"照出来（读样式表字符串会被子串匹配骗：
`.bg-rose-50` 命中的其实是 `.bg-rose-500/15`）。

**改了三处，必须一起改**：

1. `apps/admin/src/index.css` 补上那行 `@source`。
2. `packages/ui/components/Toast.tsx` 补暗色配色。它原本**只有一套亮色类名**——
   单补第 1 条会让它在暗色主题里画出一块亮色（Badge 一直是两套按 `data-theme` 选，Toast 漏了）。
   现在与 Badge 同源：`useResolvedSurfaceTheme()` 选亮/暗两张表，危险色暗侧用 `rose` 不用 `red`。
3. 新增门禁 `pnpm check:ui-source`（进 `pnpm gates`）：凡是引入 `@axiforge/ui` 令牌的应用 CSS 入口，
   都必须扫 `packages/ui/src`。变异验证：把那行换成别的源 → 门禁立刻红并点名应用。

**放行前量过的对比度**（浏览器里把颜色画进 canvas 取像素算 WCAG 比，明暗两套主题各 6 组）：
亮色 `Badge emerald 5.09 / rose 5.49 / amber 4.85 / blue 6.28 / Toast success 7.23 / error 7.64`，
暗色 `10.26 / 8.87 / 10.49 / 9.06 / 10.26 / 8.87` —— 12 组全部达 AA 正文（≥4.5），
最紧的是亮色 amber Badge 4.85:1。所以这次"让颜色第一次真的上色"没有引入不达标的配对。
运行时也验过：暗色主题点「让模型重判」，浮层底色解析为 `emerald-500/15`、文字 `emerald-300`；
亮色同一动作是 `emerald-50` + `emerald-800`。队列页抽样的 12 个彩色 span 现在 12/12 有底色。

**仍欠的**：静态对比度门禁 `check-contrast.mjs` 只认 `tokens.css` 里的 `--ax-*` 令牌，
**看不见组件里直接写死的 Tailwind 色板值**（`emerald-50`、`rose-500/15` 这类）。
这次的 12 组是我手工在浏览器里量的，没有进 CI——也就是说下次有人改这些类名，
门禁不会拦。要闭掉这一步得二选一：给门禁加 oklch/oklab 解析器并把色板配对登记进去，
或者把这些 tone 收进 `tokens.css` 变成真正的语义令牌（后者更对，但要动设计决定）。
